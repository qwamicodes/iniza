# IZ1 cryptographic library research

**Research date:** 2026-09-01
**Scope:** dependency and parameter evidence for COKS-25. This is research input for the architecture decision; it is not itself approval to protect real data.

## Recommendation

Use the following maintained Rust crates for the IZ1 prototype, with the exact resolved patch releases committed in `Cargo.lock` and reviewed again before Owner Dogfood:

| Purpose | Crate and current stable release | Recommendation |
|---|---|---|
| Authenticated encryption | [`chacha20poly1305` 0.11.0](https://index.crates.io/ch/ac/chacha20poly1305) | `XChaCha20Poly1305`, 32-byte key and 24-byte nonce; enable its `zeroize` feature. |
| Recovery-secret key derivation | [`argon2` 0.6.0](https://index.crates.io/ar/go/argon2) | Argon2id version `0x13`, explicitly configured rather than using crate defaults; enable its `zeroize` feature. |
| Context-separated subkeys | [`hkdf` 0.13.0](https://index.crates.io/hk/df/hkdf) with [`sha2` 0.11.0](https://index.crates.io/sh/a2/sha2) | HKDF-SHA-256 with a Bundle-specific salt and fixed, versioned `info` labels. |
| Non-secret hashes | [`blake3` 1.8.7](https://index.crates.io/bl/ak/blake3) | Unkeyed 32-byte hashes for content identity, exact-prefix sealing input, whole-Bundle comparison, and Receipts; enable `zeroize` only if keyed modes are later used. |
| Operating-system randomness | [`getrandom` 0.4.3](https://index.crates.io/ge/tr/getrandom) | Call `getrandom::fill` directly for every data-encryption key, recovery secret, salt, Bundle identifier, and random nonce; fail the operation on any error. |
| Secret erasure | [`zeroize` 1.9.0](https://index.crates.io/ze/ro/zeroize) | Keep plaintext recovery secrets, wrapping keys, the data-encryption key, and derived keys in fixed-capacity `Zeroizing` values and minimize copies. |

The selected set has an effective Rust 1.85 floor in current crate metadata. Argon2 0.6.0 was released on 2026-08-27, so it has little stable-release bake time; pin and test it deliberately, and do not treat “latest” as an audit result. The RustCrypto XChaCha20-Poly1305 crate documents one NCC Group audit with no significant findings, but that audit predates 0.11.0 and is not a review of Iniza's format or key lifecycle ([crate security notes](https://docs.rs/crate/chacha20poly1305/latest)).

## Proposed IZ1 parameters and key schedule

1. Generate a fresh 32-byte data-encryption key, two independent 32-byte recovery secrets, a 32-byte HKDF salt, a 16-byte random Bundle identifier, two independent 16-byte Argon2 salts, and all random nonce material with `getrandom::fill`. The function uses the operating system's preferred source, reports partial reads as errors, and may block during early boot ([`getrandom::fill`](https://docs.rs/getrandom/latest/getrandom/fn.fill.html)). On the target platforms, the crate uses `getentropy` on macOS and the `getrandom` system call on Linux, with a guarded fallback on supported Linux targets ([official target table](https://github.com/rust-random/getrandom#supported-targets)).
2. For each Recovery Method independently, derive a 32-byte wrapping key using Argon2id version `0x13`, a slot-specific 16-byte salt, `m = 65,536 KiB`, `t = 3`, and `p = 4`. These are the second recommended RFC 9106 settings: 64 MiB memory, three passes, four lanes, 128-bit salt, and a 256-bit tag ([RFC 9106, Sections 3 and 4](https://www.rfc-editor.org/rfc/rfc9106.html#section-4)). Serialize and authenticate all parameters. A reader must reject parameters outside IZ1 bounds before allocating memory; it must never honor attacker-selected unbounded costs.
3. Wrap the same data-encryption key once per slot with XChaCha20-Poly1305 under that slot's derived wrapping key. Use an independent random 24-byte nonce per slot. Authenticate the fixed preamble, suite identifier, Bundle identifier, slot identifier and kind, Argon2 version/algorithm/parameters/salt, wrapped-key plaintext length, and nonce as canonical associated data.
4. Run HKDF-SHA-256 with the data-encryption key as input keying material and the random 32-byte Bundle HKDF salt. Derive separate 32-byte keys with exact fixed labels such as `iniza IZ1 content key`, `iniza IZ1 manifest key`, `iniza IZ1 index key`, and `iniza IZ1 completion key`, each followed by the Bundle identifier. RFC 5869 recommends the extract step with salt and requires application-specific `info` for separation; SHA-256 output is 32 bytes and the maximum expansion is 8,160 bytes ([RFC 5869, Sections 2 and 3](https://www.rfc-editor.org/rfc/rfc5869.html)).
5. Use a 16-byte random Bundle nonce prefix followed by one unsigned 64-bit big-endian global record sequence number to form every 24-byte content nonce. Never reuse a sequence number under a derived key. XChaCha uses a 192-bit nonce, and its draft permits random nonces with a much lower collision risk than 96-bit ChaCha20-Poly1305 ([XChaCha draft, Sections 2 and 2.1](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-xchacha-03#section-2)). The RustCrypto type is exactly 24 bytes ([`XNonce`](https://docs.rs/chacha20poly1305/latest/chacha20poly1305/type.XNonce.html)).
6. Authenticate, for every encrypted record, a canonical binary schema containing the fixed preamble hash, suite and format version, Bundle identifier, record kind, global sequence number, item identifier where applicable, plaintext length, and ciphertext length. Associated data is authenticated but not encrypted; therefore it must contain no path, username, hostname, or other confidential metadata. The application is responsible for structuring associated data ([RFC 8439 AEAD limits and associated-data guidance](https://www.rfc-editor.org/rfc/rfc8439.html#section-2.8)).
7. Start the prototype with a 1 MiB maximum plaintext chunk. This is an Iniza engineering choice, not a cryptographic requirement: it bounds allocation and corruption scope while avoiding excessive records for multi-gigabyte Bundles. Exercise zero-length, one-byte, boundary-minus-one, boundary, and boundary-plus-one cases. Revisit the value with benchmarks before freezing IZ1; changing it after format approval requires explicit compatibility treatment.
8. Compute BLAKE3 over the exact serialized bytes preceding the completion record. Encrypt and authenticate that digest, the final record count, manifest/index locations, and the `complete` state with the completion key. A bare BLAKE3 digest is not an authenticator because an attacker can recompute it. Only a valid completion record makes a Bundle `Sealed`; partial output must retain a distinct filename and must not be accepted by normal Inspect, Verify, or Restore.

## Nonce, authentication, and parser constraints

- XChaCha20-Poly1305 still catastrophically loses confidentiality and integrity if a key/nonce pair repeats. The longer nonce makes safe random generation practical; it does not make reuse harmless. The underlying ChaCha20-Poly1305 limits one invocation to about 256 GiB and requires unique nonces ([RFC 8439, Sections 2.8 and 4](https://www.rfc-editor.org/rfc/rfc8439.html#section-2.8)); IZ1's 1 MiB record bound is far below that limit.
- A record is not trusted until its tag verifies. Decryption must not release plaintext to Restore or parse paths/counts from encrypted metadata before authentication. Record type and sequence in associated data make substitution and reordering fail authentication; the authenticated completion record makes removal, truncation, duplication, or forged completion fail closed.
- Parse only a fixed-size preamble before unlock. Bound all lengths before conversion or allocation. For this spike, recommended hard limits are: 4 KiB public header, 8 recovery slots, 4 KiB per slot record excluding its fixed wrapped key, 1 MiB plaintext chunk plus the 16-byte tag, 16 MiB encrypted manifest, and 64 MiB encrypted index. Reject non-canonical encodings, unknown critical flags, duplicate slot identifiers, sequence gaps, integer overflow, trailing bytes after completion, and any suite/version not explicitly supported.
- Argon2 cost fields are denial-of-service inputs until bounded. IZ1 readers should accept only the documented version/algorithm and a deliberately narrow supported cost range, with the prototype writer emitting the exact recommended values above.

## Known-answer and adversarial vectors

Commit small, non-secret vectors with provenance and also retain an end-to-end golden Bundle:

- XChaCha20-Poly1305: use the developer-friendly authenticated-encryption vector in Appendix A.3.1 of the [XChaCha Internet-Draft](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-xchacha-03#appendix-A.3.1). Add accepted and rejected cases from [C2SP Project Wycheproof](https://github.com/C2SP/wycheproof), which explicitly covers XChaCha20-Poly1305 and known attack classes. RustCrypto added Wycheproof coverage in 0.8.0 ([crate changelog](https://github.com/RustCrypto/AEADs/blob/master/chacha20poly1305/CHANGELOG.md)).
- Argon2id: use the version 19 vector in [RFC 9106, Section 5.3](https://www.rfc-editor.org/rfc/rfc9106.html#section-5.3) and cross-check the maintained [RustCrypto known-answer tests](https://github.com/RustCrypto/password-hashes/blob/master/argon2/tests/kat.rs).
- HKDF-SHA-256: use RFC 5869 Appendix A test cases, including the basic, long-input, and zero-length salt/info cases ([RFC 5869 Appendix A](https://www.rfc-editor.org/rfc/rfc5869.html#appendix-A)).
- BLAKE3: vendor selected cases from the official repository's [test-vector set](https://github.com/BLAKE3-team/BLAKE3/tree/master/test_vectors), which covers ordinary, keyed, and derive-key modes and multiple lengths. The official repository also provides a readable [reference implementation](https://github.com/BLAKE3-team/BLAKE3/blob/master/reference_impl/reference_impl.rs).
- The IZ1 golden vector must fix every normally random byte through a test-only randomness seam, then assert exact Bundle bytes, independent unlock through each Recovery Method, authenticated Inspect, full Verify, exact-byte Restore, and rejection after changing each structural field, ciphertext byte, tag, sequence, length, and completion byte. Production code must never expose deterministic randomness.

## Maintenance and review caveats

- XChaCha20-Poly1305 is specified by an expired Internet-Draft rather than a final RFC. The draft supplies interoperable vectors and explains the 192-bit construction, but the ADR must record this standards-status trade-off ([draft status and construction](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-xchacha-03)).
- The RustCrypto implementation's audit is useful evidence, not transitive assurance for current dependencies, parser logic, nonce construction, associated-data encoding, secret transport, or the Bundle state machine.
- BLAKE3's official analysis targets 128-bit security even though the default output is 256 bits ([BLAKE3 specification security goals](https://github.com/BLAKE3-team/BLAKE3-specs/blob/master/blake3.tex)). Use it for non-secret identity and authenticated sealing input, not as a replacement for authenticated encryption or Argon2.
- `zeroize` guarantees that its overwrite is not optimized away, but does not prevent prior copies from reallocation, stack spills, registers, swap, or microarchitectural leakage. The crate recommends heap storage to reduce move copies while explicitly documenting these limits ([zeroize guarantees and stack/heap notes](https://docs.rs/zeroize/latest/zeroize/#what-guarantees-does-this-crate-provide)). `Zeroizing<T>` performs zeroization on drop ([wrapper documentation](https://docs.rs/zeroize/latest/zeroize/struct.Zeroizing.html)).
- Enabling zeroization features and avoiding `Clone`, formatting, serialization, ordinary `String`, environment variables, and command arguments for secrets are format-level requirements, not properties supplied automatically by the cryptographic crates.
- COKS-25 should remain a synthetic-data technical spike. Independent cryptography/key-handling review remains required before real sole-copy data or Owner Dogfood reliance.

## Credible alternatives not selected for IZ1

| Alternative | Why it is not the first choice |
|---|---|
| AES-256-GCM | It is standardized and RustCrypto's crate has an NCC audit, but nonce reuse is catastrophic and the recommended nonce is only 96 bits. XChaCha's 192-bit nonce is a better fit for independently written Bundle records across software-only macOS and Linux implementations ([RustCrypto AES-GCM security notes](https://docs.rs/aes-gcm/latest/aes_gcm/), [RFC 8439 XChaCha motivation](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-xchacha-03#section-2.1)). |
| AES-256-GCM-SIV | It provides nonce-misuse resistance and is the strongest fallback if nonce uniqueness cannot be made convincing. It requires two encryption passes and therefore cannot encrypt a record online; IZ1 can instead enforce a simple global sequence construction under fresh per-Bundle keys ([RFC 8452, Sections 1 and Appendix B](https://www.rfc-editor.org/rfc/rfc8452.html)). |
| Plain ChaCha20-Poly1305 | It is a final RFC construction, but its 96-bit nonce must be unique and RFC 8439 says it must not be randomly generated. XChaCha retains the construction while making independently generated 192-bit nonces practical ([RFC 8439 nonce requirement](https://www.rfc-editor.org/rfc/rfc8439.html#section-2.8), [XChaCha motivation](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-xchacha-03#section-2.1)). |
| PBKDF2 or scrypt for Recovery Methods | Both have standards and mature implementations, but RFC 9106 selects Argon2id as its uniformly safe, side-channel-conscious memory-hard recommendation. There is no compatibility requirement forcing a legacy password derivation function for a new Bundle format ([RFC 9106 parameter selection](https://www.rfc-editor.org/rfc/rfc9106.html#section-4)). |
| BLAKE3 as the password derivation function | The official BLAKE3 project explicitly says it is intentionally fast and recommends Argon2 for password/key derivation from passwords ([official BLAKE3 README](https://github.com/BLAKE3-team/BLAKE3#blake3)). |

## Decision conditions

IZ1 is a reasonable prototype suite if the architecture decision fixes the byte-level associated-data schemas, nonce sequence rules, parser bounds, exact crate versions, golden vectors, and immutable compatibility behavior. It is not ready for owner acceptance until the prototype demonstrates both independent slot unlocks and every required fail-closed mutation, and the owner explicitly accepts the ADR's expired-draft, recent-dependency, and independent-review caveats.
